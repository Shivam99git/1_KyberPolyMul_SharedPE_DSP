# Baseline definition: the per-phase reference core

The resource-sharing claim of the manuscript is a *comparison*: the shared-PE core against a
reference core that computes exactly the same function with the same control but a dedicated
arithmetic unit for each phase. This document states precisely what the two cores share, what
differs, and under which conditions the numbers were obtained, so that the fairness of the
comparison can be judged.

Files: shared-PE `rtl/shared_pe/ntt_core_shared.v` (module `ntt_core_shared`), per-phase
reference `rtl/per_phase_baseline/ntt_core_baseline.v` (module `ntt_core_baseline`).

## What is identical

| Item | Both cores |
|---|---|
| Algorithm / schedule | forward NTT(f), forward NTT(g), base multiplication, inverse NTT, scaling — strictly sequential, same order of butterflies and coefficient pairs |
| Control FSM | the same 38 states, the same state encoding, the same counters (`layer`, `len_reg`, `start_reg`, `j_reg`, `k_idx`, `bm_i`, `scale_idx`, `target_sel`), the same next-state logic |
| Cycle count | 27 269 clock cycles per product (measured in RTL simulation for both; `results/csv/cycle_counts.csv`) |
| Memories | `mem_a`, `mem_b`: 256 × 12 bit, one write port, two asynchronous read ports, distributed LUT RAM (256 LUTs as memory, 0 BRAM) |
| Twiddle ROM | the same `zeta_rom` module and the same `.mem` images |
| Working registers | `wa wb wc wd w_t w_sum w_diff w_m1 w_za1b1 w_a0b0 w_a0b1 w_a1b0` and the multiplier operand registers `mult_op_a`, `mult_op_b` |
| Elementary modules | the same `mult_unit` → `mult_conventional` (12×12 product + Barrett, 3 DSP48E1), `mod_add`, `mod_sub` |
| Ports | identical port list |
| Test vectors | the same 256 vectors (`data/test_vectors/multi_*.mem`); both cores pass with 0 mismatches over 65 536 coefficients each |
| Device, tool, flow | Artix-7 `xc7a35tcpg236-1`, Vivado 2024.2, in-memory project, `synth_design -mode out_of_context`, clock constraint read before synthesis, default synthesis and implementation settings (no directives, no strategies), `opt_design` → `place_design` → `route_design` |
| Clock constraint | `create_clock -period 10.000 -name clk [get_ports clk]` for every area / power / slack comparison (`constraints/clk_10ns.xdc`); each core's own closed period is found by the same search procedure and is used for Fmax and latency |

## What differs

| | Shared-PE | Per-phase reference |
|---|---|---|
| Modular multipliers (`mult_unit`) | **1** | **4**: `u_mult_ntt`, `u_mult_bm`, `u_mult_intt`, `u_mult_scale` |
| DSP48E1 | 3 | 12 (3 per multiplier) |
| Modular adders (`mod_add`) | **1** (`u_add`) | **4**: CT `a+t`, GS `a+b`, PWM `c0`, PWM `c1`, each with fixed operands |
| Modular subtractors (`mod_sub`) | **1** (`u_sub`) | **2**: CT `a−t`, GS `b−a`, each with fixed operands |
| Add/sub operand multiplexers | four (adder A 3:1, adder B 4:1, subtractor A 2:1, subtractor B 2:1) selected by the FSM state | none (operands hard-wired per unit) |
| Result selectors | none | `add_y` (4:1), `sub_y` (2:1), multiplier `done` and `result` (4:1 each), selected by the phase / state |
| Multiplier start | one `mult_start` | `mult_start` gated by the current phase for each multiplier |

The multiplier operand registers `mult_op_a` / `mult_op_b` and the FSM logic that loads them
(a 4:1 and a 6:1 selection of working registers, ROM outputs and `N_INV`) are the same in both
cores: in the per-phase core the two operand registers feed all four multipliers, of which only
the one belonging to the current phase is started. Consequently the multiplexing that the per-phase
core saves is the four add/sub operand multiplexers, and it adds result selectors in exchange;
"sharing" in the manuscript's comparison therefore means replicated arithmetic units
(multipliers, adders, subtractors) versus time-multiplexed ones, with the selection logic that
each style needs. The module-group attribution in `results/csv/hierarchy_summary.csv`
(manuscript Table VIII) shows where the LUTs go.

## Synthesis and implementation strategy

* Same Tcl procedure for every core (`scripts/synthesis/flow_common.tcl`): `read_verilog -sv`,
  `read_xdc` (clock only), `synth_design -top <top> -part xc7a35tcpg236-1 -mode out_of_context
  [-verilog_define USE_PIPELINED_BARRETT]`, `opt_design`, `place_design`, `route_design`, then
  `report_utilization` (flat and hierarchical), `report_timing_summary`, `report_timing`,
  `report_route_status`, `report_clock_utilization`, `report_power` (text and XML).
* Closure search: shared and per-phase cores fail 10 ns, so the period is relaxed by
  `period ← period − WNS + 0.050 ns` until WNS ≥ 0; the pipelined core already meets 10 ns, so its
  period is tightened in 0.2 ns steps from 9.5 ns until a run fails. The closed period is the
  smallest period at which a run met timing.
* Power: Vivado's post-route vectorless estimate at 10 ns (`report_power`, confidence "Medium"),
  converted from the per-rail supply currents so that dynamic + static = total exactly. An
  activity-annotated cross-check (SAIF from RTL simulation, both cores at their common closed
  period) is in `scripts/power/` and is described in `docs/reproducibility.md`.

## Provenance and limits of the comparison

* **Provenance.** `ntt_core_baseline.v` was written for this comparison from the architecture
  description so that sharing is the only variable. A reference core of earlier project snapshots
  (whose schedule differed and whose RTL could not be recovered) is not used in this release;
  every per-phase number in the manuscript is measured on `ntt_core_baseline.v`.
* **One run per configuration.** Each number is one place-and-route run (one placement seed, the
  tool's default). The flows are deterministic for a given Vivado release (the regenerated reports
  reproduce the archived ones exactly), but this is not a statistical sample over placements.
* **The 10 ns target is not met by the shared or per-phase core.** Area and power are therefore
  those of a timing-failing 10 ns implementation, as stated in the manuscript; Fmax and latency use
  each core's own closed period.
* **Vectorless power** reflects default toggle rates, not the activity of this workload. The SAIF
  cross-check annotates only the nets whose names match between the RTL simulation and the
  post-synthesis netlist (19 % of the nets of the shared core, 13 % of the per-phase core in the
  archived run), so it too is an estimate.
* **Out-of-context implementation** without I/O buffers: the numbers describe the block, not an
  integrated system.
